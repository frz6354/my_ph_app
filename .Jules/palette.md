## 2026-07-20 - Adding Empty State for Better Onboarding
**Learning:** React Native applications without default content (like an empty zip code list in a weather app) can feel broken or uninviting to new users. Adding an empty state with a helpful call-to-action significantly improves the onboarding experience and clearly directs the user on how to get started.
**Action:** Always consider empty states for dynamic lists or data-driven views to provide context and guidance when data is not yet available.

## 2026-07-25 - Handling Async UI States
**Learning:** For async actions (like adding a zip code and fetching remote weather data simultaneously), quick repeated taps can queue up multiple backend calls. Disabling UI elements (e.g., adding `editable={!isSubmitting}` to `TextInput` and `disabled={isSubmitting}` to buttons) and providing clear visual feedback (via `ActivityIndicator`) not only prevents accidental duplicate actions but immediately reassures the user that their action is being processed.
**Action:** When wiring up async submission handlers, always use a `try/finally` block to manage an `isSubmitting` boolean state, and propagate that state to disable related inputs and show loading indicators.

## 2026-07-26 - Native System Alarm Scheduling and Deduplication
**Learning:** Relying purely on background task scheduling or long-running foreground service intervals to fire precise alarms can be highly unreliable due to aggressive Android Doze mode and OS battery optimization constraints. Delegating precise alarms to the native Android system Clock application via standard `android.intent.action.SET_ALARM` Intents guarantees absolute accuracy and boot-persistent reliability. However, because native alarm intents always create a new entry inside the system Clock, running sync checks continuously within background polling routines can result in major UI duplicate flooding. Implementing a persistent deduplication layer using `AsyncStorage` to cache target ISO times prevents repetitive native registrations unless the calculated alarm time actually changes.
**Action:** Always map programmatically scheduled native system-level resources (like Intents or system settings) to a unique state identifier stored in persistent local cache, and gate system calls by verifying if the target configuration or calculated date/time has changed.

## 2026-07-27 - Debugging and Visualizing Complex API Data
**Learning:** Presenting highly detailed weather variables from a remote API can overwhelm general UI design structures if not properly categorized and formatted. Grouping extensive variables (like pressure, precipitation metrics, coordinates, astronomical conditions, and unit toggles/conversions) inside discrete card components maintains a clean information hierarchy. Furthermore, embedding an inline inspection tool—like a small, easily accessible code icon that triggers a modal containing pretty-printed raw JSON—provides developers and power users with instantaneous visual diagnostics directly in the interface without requiring debugger attachments or external proxy monitoring.
**Action:** For complex integrations, provide highly formatted grid/card categories to represent all available variables, and build clean interactive modals that serialize raw API objects into structured code-view environments for fast client-side verification.

## 2026-08-08 - Adding Confirmation Dialogs for Destructive Actions
**Learning:** Destructive actions without a confirmation step can easily lead to accidental data loss and frustrated users. Implementing simple native `Alert.alert` dialogues forces the user to confirm their intent and acts as a crucial safety net for high-stakes actions like deleting an API key or an active alarm.
**Action:** For all actions that modify or delete critical persistent state (such as settings or keys), enforce the use of a native confirmation prompt with explicit "Cancel" and "Delete" (or equivalent destructive) options.
